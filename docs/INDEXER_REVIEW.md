## Актуальный статус

| Пункт | Статус и подтверждение |
|---|---|
| Перенос/удаление дерева и корня | DELETE запрашивает сверку родителя. Потеря регистрации корня вызывает RootWatchLostException; supervisor автоматически останавливает сервис. Вложенное удаление не должно останавливать наблюдение за корнем. |
| Ошибка ленивого обхода reconciliation | Исправлено для `UncheckedIOException`: обработчик продолжает очистку состояния; последующий запрос того же пути работает. Произвольные RuntimeException по-прежнему не гарантируют очистку. |
| Ошибка initial scan | Producer публикует future успеха, IOException, причины UncheckedIOException, RuntimeException или interruption. Сервис ждёт его или workerFailure через anyOf, сохраняет исходную причину и выполняет cleanup. |
| MODIFY папки folder.md и смена типа | Watcher фильтрует директории. FileProcessor читает BasicFileAttributes одной операцией и отвергает не обычный файл через NotRegularFileException; Worker удаляет старую запись без recovery. |
| Регистрация watcher | WatchRegistrar преобразует UncheckedIOException в IOException. Сервис получает ошибки startup, включая RuntimeException, и останавливает частично запущенные ресурсы. |
| Барьеры и заполненные очереди | Общий BarrierTask использует AtomicInteger и completion future. Отправка offer согласована с STARTING; повторные попытки проверяют workerFailure. Проверены падение Worker, shutdown и успешное освобождение очереди. |
| StopTask при падении Worker | Завершившийся Worker пропускается; живому отправляется StopTask через offer с таймаутом и повторной проверкой состояния. Проверены interruption и полная очередь. |
| Консольные сессии | Main читает события одной очереди, различает сессии по runId, возвращается к запросу пути и завершает приложение по EOF. Семь process-тестов запускают отдельную JVM. |
| Относительный корень | Исправлено: абсолютный нормализованный корень передаётся producer и watcher. Три теста проверяют relative root, сегмент `..` и файл, созданный после start. |
| Согласованность snapshot | Исправлено: workers и snapshot используют общий indexStateLock. Тесты подтверждают ожидание между обновлением map и статистики и отсутствие блокировки при чтении файла. Снимок согласован с индексом, не с одновременно изменяющимся диском. |

## Осталось до фиксации основы

1. Подключить workerFailure к supervisor после RUNNING; сейчас он ждёт только
   termination watcher. Вынести перехват RuntimeException за границы всего
   рабочего цикла, включая ошибки внутри обработчиков IOException.
2. Гарантировать очистку статуса reconciliation при произвольном RuntimeException.
3. Обрабатывать исчезновение вложенной директории во время регистрации локально,
   не завершая наблюдение за существующим корнем.
4. Уточнить контракт shutdown: ошибки отдельных стадий cleanup, таймаут executor,
   публикация termination при конкурентных вызовах и общий срок ожидания.
5. Определить политику symbolic links и недоступных путей scanner.
6. Зафиксировать промежуточный коммит; после следующих исправлений повторить regression-прогон.

## Что выглядит корректно в проверенном коде

- Router направляет одинаковый Path в одну FIFO-очередь.
- Worker использует предыдущую запись для upsert и изменения размера.
- Повторный DELETE не уменьшает статистику второй раз.
- NoSuchFileException удаляет старую запись, обычная IOException сохраняет её.
- Индекс владеет Map, статистика скрывает атомики.
- Debounce отменяет ожидающую задачу и не позволяет старому callback удалить новую.
- Recovery ограничивает попытки и передаёт исчерпание родительскому reconciliation.
- Остановка запрещает новые запросы, затем останавливает источники и Worker.

Это оценка реализации, а не гарантия отсутствия других гонок. Shutdown ожидает
Worker без общего предельного времени; неожиданное завершение Worker или
зависание операции может привести к бесконечному ожиданию.
