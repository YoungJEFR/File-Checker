# File Indexer — Progress

Учебный pet-проект на Java.

Изначально проект начинался как простой обход файлов, но постепенно вырос в
многопоточный индексатор, который отслеживает изменения файлов в реальном времени.

Главная цель проекта — не просто использовать как можно больше классов из
`java.util.concurrent`, а разобраться, какие проблемы возникают в настоящем
многопоточном приложении и как их решать.

---

## Сейчас

Уже работает:

- первоначальное сканирование директории;
- построение индекса файлов;
- несколько Worker-потоков;
- передача задач через `BlockingQueue`;
- обновление индекса при создании, изменении и удалении файлов;
- `WatchService`;
- debounce частых `MODIFY`;
- потокобезопасный индекс;
- статистика количества файлов и общего размера;
- корректная остановка основных компонентов;
- блокировка обработки одного и того же файла несколькими Worker одновременно.

Сейчас работаю над:

**сохранением порядка событий одного файла при нескольких Worker-потоках.**

Например:

```text
MODIFIED notes.md
DELETED notes.md
```

должны быть обработаны именно в таком порядке, при этом события разных файлов
должны продолжать выполняться параллельно.

# Этап 7 — Debounce изменений

`WatchService` может отправлять много `ENTRY_MODIFY` для одного сохранения файла.

Например:

```text
MODIFY notes.md
MODIFY notes.md
MODIFY notes.md
MODIFY notes.md
```

Обрабатывать каждое событие нет смысла.

- [x] Разобраться, что такое debounce
- [x] Изучить `ScheduledExecutorService`
- [x] Изучить `ScheduledFuture`
- [x] Хранить ожидающие задачи по `Path`
- [x] Отменять предыдущий `MODIFY`
- [x] Выполнять обработку после 500 мс тишины
- [x] Не блокировать поток `FileWatcher`
- [x] При `DELETE` отменять ожидающий `MODIFY`
- [x] После debounce возвращать `FileTask` в обычную очередь

Получилось:

```text
MODIFY
   ↓
debounce
   ↓
500 ms без новых изменений
   ↓
BlockingQueue
   ↓
Worker
```

# Этап 8 — Согласованность при нескольких Worker

Здесь проект начал упираться уже в реальные проблемы многопоточности.

`ConcurrentHashMap` делает отдельные операции потокобезопасными, но последовательность:

```text
прочитать старое значение
↓
обработать файл
↓
изменить статистику
↓
записать новое значение
```

сама по себе атомарной не является.

### Уже сделано

- [x] Создать `PathLockManager`
- [x] Хранить `ReentrantLock` для каждого `Path`
- [x] Использовать `computeIfAbsent()`
- [x] Запретить двум Worker одновременно обрабатывать один файл
- [x] Оставить параллельную обработку разных файлов

Например:

```text
Worker-1 → a.md ─┐
                 ├─ один lock
Worker-2 → a.md ─┘

Worker-3 → b.md → другой lock
```

### Сейчас

- [ ] Гарантировать порядок событий одного `Path`

Проблемный сценарий:

```text
queue:

1. MODIFIED a.md
2. DELETED a.md
```

Два Worker могут забрать их в правильном порядке, но начать выполнение уже
в обратном.

Нужно получить гарантию:

```text
один Path
→ строго последовательная обработка

разные Path
→ параллельная обработка
```

Варианты, которые хочу исследовать:

- [ ] partitioning задач между Worker
- [ ] очередь событий на `Path`
- [ ] общий пул Worker + последовательная обработка задач одного ключа
- [ ] балансировка нагрузки без нарушения порядка

# Журнал проблем

По ходу проекта полезно сохранять не только то, что было написано, но и почему
пришлось что-то менять.

```text
Дата:

Проблема:

Почему возникла:

Как решил:

Что понял:
```

Например:

```text
Проблема:
WatchService отправлял несколько MODIFY подряд после одного сохранения файла.

Почему возникла:
Одно логическое изменение файла может породить несколько событий файловой системы.

Как решил:
Добавил debounce через ScheduledExecutorService и ScheduledFuture.

Что понял:
События файловой системы нельзя воспринимать как точную историю действий пользователя.
Иногда поток событий нужно нормализовать перед обработкой.
```
